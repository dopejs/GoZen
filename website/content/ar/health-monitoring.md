# مراقبة السلامة وموازنة الأحمال

راقب سلامة المزوّدين لحظيًا ووجّه الطلبات تلقائيًا إلى أفضل مزوّد متاح.

## المزايا

- **فحوص سلامة لحظية** — مراقبة دورية بفواصل زمنية قابلة للضبط
- **تتبّع نسبة النجاح** — تُحسب السلامة من نسبة الطلبات الناجحة
- **مراقبة الكمون** — متوسط زمن الاستجابة لكل مزوّد
- **استراتيجيات متعددة** — التحويل عند الفشل، والتناوب الدوري، وأقل كمون، وأقل تكلفة
- **تحويل تلقائي** — الانتقال إلى مزوّدين احتياطيين حين يصبح الأساسي غير سليم
- **لوحة سلامة** — مؤشرات حالة بصرية في واجهة الويب

## الإعداد

### تفعيل مراقبة السلامة

```json
{
  "health_check": {
    "enabled": true,
    "interval": "5m",
    "timeout": "10s",
    "endpoint": "/v1/messages",
    "method": "POST"
  }
}
```

**الخيارات:**
- `interval` — عدد مرات فحص سلامة المزوّد (الافتراضي: 5 دقائق)
- `timeout` — مهلة طلب الفحص (الافتراضي: 10 ثوانٍ)
- `endpoint` — نقطة الـ API التي تُختبر (الافتراضي: `/v1/messages`)
- `method` — أسلوب HTTP المستخدم في الفحص (الافتراضي: `POST`)

### إعداد موازنة الأحمال

```json
{
  "load_balancing": {
    "strategy": "least-latency",
    "health_aware": true,
    "cache_ttl": "30s"
  }
}
```

## استراتيجيات موازنة الأحمال

### 1. التحويل عند الفشل (الافتراضي)

يستخدم المزوّدين بالترتيب، وينتقل إلى التالي عند الفشل.

```json
{
  "profiles": {
    "default": {
      "providers": ["anthropic-primary", "anthropic-backup", "openai"],
      "load_balancing": {
        "strategy": "failover"
      }
    }
  }
}
```

**السلوك:**
1. تجربة `anthropic-primary`
2. عند الفشل، تجربة `anthropic-backup`
3. عند الفشل، تجربة `openai`
4. إذا فشل الجميع، تُعاد رسالة خطأ

**الأنسب لـ:** أحمال الإنتاج ذات التسلسل الواضح بين الأساسي والاحتياطي

### 2. التناوب الدوري

يوزّع الطلبات بالتساوي على جميع المزوّدين السليمين.

```json
{
  "load_balancing": {
    "strategy": "round-robin"
  }
}
```

**السلوك:**
- الطلب 1 ← المزوّد A
- الطلب 2 ← المزوّد B
- الطلب 3 ← المزوّد C
- الطلب 4 ← المزوّد A (وتتكرر الدورة)

**الأنسب لـ:** توزيع الحمل على عدة حسابات لتفادي حدود المعدّل

### 3. أقل كمون

يوجّه إلى المزوّد صاحب أقل متوسط كمون.

```json
{
  "load_balancing": {
    "strategy": "least-latency"
  }
}
```

**السلوك:**
- يتتبّع متوسط زمن الاستجابة لكل مزوّد
- يوجّه إلى الأسرع
- يحدّث المقاييس كل 30 ثانية (قابل للضبط عبر `cache_ttl`)

**الأنسب لـ:** التطبيقات الحساسة للكمون والتفاعل اللحظي

### 4. أقل تكلفة

يوجّه إلى المزوّد الأرخص للنموذج المطلوب.

```json
{
  "load_balancing": {
    "strategy": "least-cost"
  }
}
```

**السلوك:**
- يقارن الأسعار بين المزوّدين
- يوجّه إلى الخيار الأرخص
- يأخذ في الحسبان تكلفة رموز الإدخال والإخراج معًا

**الأنسب لـ:** خفض التكلفة والمعالجة على دفعات

## حالة السلامة

يُصنَّف المزوّدون إلى أربع حالات سلامة:

| الحالة | نسبة النجاح | السلوك |
|--------|--------------|----------|
| **سليم** | ‏95% فأكثر | أولوية عادية |
| **متدهور** | ‏70%–95% | أولوية أقل، وما زال صالحًا |
| **غير سليم** | أقل من 70% | يُتخطّى ما لم يغب المزوّدون السليمون |
| **غير معروف** | لا توجد بيانات | يُعامَل مبدئيًا كسليم |

### توجيه يراعي السلامة

عندما يكون `health_aware: true` (الافتراضي):
- تُمنح الأولوية للمزوّدين السليمين
- يُستخدم المتدهورون كخيار احتياطي
- يُتخطّى غير السليمين إلا إذا فشل الجميع

## لوحة واجهة الويب

لوحة السلامة متاحة على `http://localhost:19840/health`:

### حالة المزوّد

- **مؤشر الحالة** — أخضر (سليم)، أصفر (متدهور)، أحمر (غير سليم)
- **نسبة النجاح** — نسبة الطلبات الناجحة
- **متوسط الكمون** — متوسط زمن الاستجابة بالمللي ثانية
- **آخر فحص** — الطابع الزمني لأحدث فحص
- **عدد الأخطاء** — عدد الإخفاقات الأخيرة

### الخط الزمني للمقاييس

- **رسم الكمون** — اتجاهات زمن الاستجابة عبر الوقت
- **رسم نسبة النجاح** — اتجاهات السلامة عبر الوقت
- **حجم الطلبات** — عدد الطلبات لكل مزوّد

## نقاط الـ API

```bash
GET /api/v1/health/providers
```


## إشعارات Webhook

استقبل تنبيهات عند تغيّر حالة المزوّد:

```json
{
  "webhooks": [
    {
      "enabled": true,
      "url": "https://hooks.slack.com/services/YOUR/WEBHOOK/URL",
      "events": ["provider_down", "provider_up", "failover"]
    }
  ]
}
```

**أنواع الأحداث:**
- `provider_down` — أصبح المزوّد غير سليم
- `provider_up` — عاد المزوّد إلى حالة سليمة
- `failover` — حُوّل الطلب إلى مزوّد احتياطي

## التوجيه حسب السيناريو

ادمج مراقبة السلامة مع التوجيه حسب السيناريو لتوزيع ذكي للطلبات:

```json
{
  "profiles": {
    "default": {
      "providers": ["anthropic-primary", "anthropic-backup"],
      "scenarios": {
        "thinking": {
          "providers": ["anthropic-thinking"],
          "load_balancing": {
            "strategy": "least-latency"
          }
        },
        "image": {
          "providers": ["anthropic-vision", "openai-vision"],
          "load_balancing": {
            "strategy": "failover"
          }
        }
      }
    }
  }
}
```

راجع [التوجيه حسب السيناريو](./routing.md) للتفاصيل.

## أفضل الممارسات

1. **اضبط فواصل مناسبة** — 5 دقائق تكفي غالبًا، ودقيقة واحدة للأنظمة الحرجة
2. **استخدم التوجيه المراعي للسلامة** — فعّله دائمًا في الإنتاج
3. **راقب المزوّدين المتدهورين** — تحقّق حين تهبط نسبة النجاح دون 95%
4. **اجمع بين الاستراتيجيات** — التحويل عند الفشل للأساسي/الاحتياطي، والتناوب لتوزيع الحمل
5. **فعّل الـ webhooks** — اعرف فورًا حين يسقط مزوّد
6. **تفقّد اللوحة بانتظام** — راجع الاتجاهات لاكتشاف الأنماط

## معالجة المشكلات

### فشل فحوص السلامة

1. تأكد من صلاحية مفاتيح API للمزوّدين
2. تحقّق من الاتصال الشبكي بنقاط نهاية المزوّدين
3. زد المهلة إذا كان المزوّدون بطيئين: `"timeout": "30s"`
4. راجع سجلات الخدمة بحثًا عن رسائل الخطأ المحددة

### مقاييس كمون غير صحيحة

1. يشمل الكمون زمن الشبكة وزمن المعالجة في الـ API
2. تحقّق مما إذا كان وسيط أو VPN يضيف عبئًا
3. تُخزَّن المقاييس مؤقتًا 30 ثانية افتراضيًا (قابل للضبط عبر `cache_ttl`)

### التحويل عند الفشل لا يعمل

1. تأكد من `health_aware: true` في إعداد موازنة الأحمال
2. تأكد من إعداد مزوّدين احتياطيين في ملف التعريف
3. تأكد من تفعيل فحوص السلامة وعملها
4. راجع أحداث التحويل في واجهة الويب أو السجلات

### مزوّد عالق في حالة غير سليمة

1. شغّل فحص سلامة يدويًا عبر الـ API
2. تحقّق مما إذا كان المزوّد متوقفًا فعلًا (اختبره بـ curl)
3. أعد تشغيل الخدمة لإعادة ضبط الحالة: `zen daemon restart`
4. راجع سجلات الأخطاء لمعرفة السبب الجذري

## الأثر على الأداء

- **فحوص السلامة** — عبء ضئيل، تعمل في goroutine بالخلفية
- **تخزين المقاييس مؤقتًا** — مهلة 30 ثانية تقلّل استعلامات قاعدة البيانات
- **عمليات ذرّية** — عدّادات آمنة للطلبات المتزامنة
- **بلا حجب** — لا تعطّل فحوص السلامة معالجة الطلبات
