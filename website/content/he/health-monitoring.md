# ניטור תקינות ואיזון עומסים

עקבו אחרי תקינות הספקים בזמן אמת ונתבו בקשות אוטומטית לספק הזמין הטוב ביותר.

## יכולות

- **בדיקות תקינות בזמן אמת** — ניטור תקופתי במרווחים שניתן להגדיר
- **מעקב אחוזי הצלחה** — התקינות מחושבת לפי שיעור הבקשות שהצליחו
- **ניטור השהיה** — זמן תגובה ממוצע לכל ספק
- **כמה אסטרטגיות** — מעבר לגיבוי, סבב מחזורי, השהיה מזערית, עלות מזערית
- **מעבר אוטומטי לגיבוי** — מעבר לספקי גיבוי כשהספק הראשי אינו תקין
- **לוח תקינות** — חיווי חזותי בממשק הווב

## הגדרה

### הפעלת ניטור התקינות

```json
{
  "health_check": {
    "enabled": true,
    "interval": "5m",
    "timeout": "10s",
    "endpoint": "/v1/messages",
    "method": "POST"
  }
}
```

**אפשרויות:**
- `interval` — תדירות בדיקת התקינות (ברירת מחדל: 5 דקות)
- `timeout` — זמן קצוב לבקשת הבדיקה (ברירת מחדל: 10 שניות)
- `endpoint` — נקודת ה-API שנבדקת (ברירת מחדל: `/v1/messages`)
- `method` — שיטת ה-HTTP לבדיקה (ברירת מחדל: `POST`)

### הגדרת איזון העומסים

```json
{
  "load_balancing": {
    "strategy": "least-latency",
    "health_aware": true,
    "cache_ttl": "30s"
  }
}
```

## אסטרטגיות איזון עומסים

### 1. מעבר לגיבוי (ברירת מחדל)

משתמש בספקים לפי הסדר ועובר לבא בתור בעת כשל.

```json
{
  "profiles": {
    "default": {
      "providers": ["anthropic-primary", "anthropic-backup", "openai"],
      "load_balancing": {
        "strategy": "failover"
      }
    }
  }
}
```

**התנהגות:**
1. לנסות את `anthropic-primary`
2. אם נכשל, לנסות את `anthropic-backup`
3. אם נכשל, לנסות את `openai`
4. אם כולם נכשלו, להחזיר שגיאה

**מתאים במיוחד ל:** עומסי ייצור עם היררכיה ברורה של ראשי וגיבוי

### 2. סבב מחזורי

מחלק בקשות באופן שווה בין כל הספקים התקינים.

```json
{
  "load_balancing": {
    "strategy": "round-robin"
  }
}
```

**התנהגות:**
- בקשה 1 ← ספק A
- בקשה 2 ← ספק B
- בקשה 3 ← ספק C
- בקשה 4 ← ספק A (המחזור חוזר)

**מתאים במיוחד ל:** פיזור עומס בין כמה חשבונות כדי לא להיתקל במגבלות קצב

### 3. השהיה מזערית

מנתב לספק בעל ההשהיה הממוצעת הנמוכה ביותר.

```json
{
  "load_balancing": {
    "strategy": "least-latency"
  }
}
```

**התנהגות:**
- עוקב אחרי זמן התגובה הממוצע לכל ספק
- מנתב לספק המהיר ביותר
- מעדכן מדדים כל 30 שניות (ניתן להגדרה דרך `cache_ttl`)

**מתאים במיוחד ל:** יישומים רגישים להשהיה ואינטראקציה בזמן אמת

### 4. עלות מזערית

מנתב לספק הזול ביותר עבור המודל המבוקש.

```json
{
  "load_balancing": {
    "strategy": "least-cost"
  }
}
```

**התנהגות:**
- משווה מחירים בין ספקים
- מנתב לאפשרות הזולה ביותר
- מתחשב בעלות אסימוני הקלט והפלט כאחד

**מתאים במיוחד ל:** אופטימיזציית עלויות ועיבוד באצווה

## מצבי תקינות

הספקים מסווגים לארבעה מצבי תקינות:

| מצב | אחוז הצלחה | התנהגות |
|--------|--------------|----------|
| **תקין** | ‏95% ומעלה | עדיפות רגילה |
| **מוחלש** | ‏70%–95% | עדיפות נמוכה יותר, עדיין שמיש |
| **לא תקין** | מתחת ל-70% | מדולג אלא אם אין ספקים תקינים |
| **לא ידוע** | אין נתונים | נחשב תקין בהתחלה |

### ניתוב מודע לתקינות

כאשר `health_aware: true` (ברירת המחדל):
- לספקים תקינים ניתנת עדיפות
- ספקים מוחלשים משמשים כגיבוי
- ספקים לא תקינים מדולגים אלא אם כל האחרים נכשלו

## לוח המחוונים בממשק הווב

לוח התקינות נמצא בכתובת `http://localhost:19840/health`:

### מצב הספק

- **חיווי מצב** — ירוק (תקין), צהוב (מוחלש), אדום (לא תקין)
- **אחוז הצלחה** — שיעור הבקשות שהצליחו
- **השהיה ממוצעת** — זמן תגובה ממוצע במילישניות
- **בדיקה אחרונה** — חותמת הזמן של הבדיקה האחרונה
- **מספר שגיאות** — כמות הכשלים האחרונים

### ציר זמן של מדדים

- **גרף השהיה** — מגמות זמן תגובה לאורך זמן
- **גרף אחוזי הצלחה** — מגמות תקינות לאורך זמן
- **נפח בקשות** — בקשות לכל ספק

## התראות webhook

קבלו התראות כשמצב ספק משתנה:

```json
{
  "webhooks": [
    {
      "enabled": true,
      "url": "https://hooks.slack.com/services/YOUR/WEBHOOK/URL",
      "events": ["provider_down", "provider_up", "failover"]
    }
  ]
}
```

**סוגי אירועים:**
- `provider_down` — הספק הפך ללא תקין
- `provider_up` — הספק חזר למצב תקין
- `failover` — הבקשה הועברה לספק גיבוי

## ניתוב מבוסס תרחיש

שלבו ניטור תקינות עם ניתוב לפי תרחיש לחלוקה חכמה של הבקשות:

```json
{
  "profiles": {
    "default": {
      "providers": ["anthropic-primary", "anthropic-backup"],
      "scenarios": {
        "thinking": {
          "providers": ["anthropic-thinking"],
          "load_balancing": {
            "strategy": "least-latency"
          }
        },
        "image": {
          "providers": ["anthropic-vision", "openai-vision"],
          "load_balancing": {
            "strategy": "failover"
          }
        }
      }
    }
  }
}
```

לפרטים ראו [ניתוב לפי תרחיש](./routing.md).

## המלצות

1. **בחרו מרווח מתאים** — 5 דקות מספיקות לרוב, דקה אחת למערכות קריטיות
2. **השתמשו בניתוב מודע לתקינות** — הפעילו תמיד בסביבת ייצור
3. **עקבו אחרי ספקים מוחלשים** — בדקו כשאחוז ההצלחה יורד מתחת ל-95%
4. **שלבו אסטרטגיות** — מעבר לגיבוי לראשי/גיבוי, סבב מחזורי לפיזור עומס
5. **הפעילו webhooks** — קבלו התראה מיידית כשספק נופל
6. **בדקו את לוח המחוונים** — עקבו אחרי מגמות כדי לזהות דפוסים

## פתרון תקלות

### בדיקות התקינות נכשלות

1. ודאו שמפתחות ה-API של הספקים תקפים
2. בדקו קישוריות רשת אל נקודות הקצה של הספקים
3. הגדילו את הזמן הקצוב אם הספקים איטיים: `"timeout": "30s"`
4. עברו על יומני הדימון לאיתור הודעות שגיאה מדויקות

### מדדי השהיה שגויים

1. ההשהיה כוללת זמן רשת וזמן עיבוד ב-API
2. בדקו אם פרוקסי או VPN מוסיפים תקורה
3. המדדים נשמרים במטמון ל-30 שניות כברירת מחדל (ניתן להגדרה דרך `cache_ttl`)

### המעבר לגיבוי אינו עובד

1. ודאו `health_aware: true` בהגדרות איזון העומסים
2. ודאו שהוגדרו ספקי גיבוי בפרופיל
3. ודאו שבדיקות התקינות מופעלות ורצות
4. עברו על אירועי המעבר בממשק הווב או ביומנים

### ספק תקוע במצב לא תקין

1. הפעילו בדיקת תקינות ידנית דרך ה-API
2. בדקו אם הספק באמת מושבת (למשל עם curl)
3. הפעילו מחדש את הדימון כדי לאפס את המצב: `zen daemon restart`
4. עברו על יומני השגיאות לאיתור שורש הבעיה

## השפעה על הביצועים

- **בדיקות תקינות** — תקורה מזערית, רצות ב-goroutine ברקע
- **מטמון מדדים** — ‏TTL של 30 שניות מפחית שאילתות למסד
- **פעולות אטומיות** — מונים בטוחים לשימוש מקבילי
- **ללא חסימה** — בדיקות התקינות אינן מעכבות טיפול בבקשות
