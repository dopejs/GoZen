# Мониторинг здоровья и балансировка нагрузки

Следите за состоянием провайдеров в реальном времени и автоматически направляйте запросы лучшему доступному провайдеру.

## Возможности

- **Проверки в реальном времени** — периодический мониторинг с настраиваемым интервалом
- **Учёт доли успешных запросов** — состояние вычисляется по доле успешных ответов
- **Мониторинг задержки** — среднее время ответа по каждому провайдеру
- **Несколько стратегий** — переключение при отказе, круговой перебор, минимальная задержка, минимальная стоимость
- **Автоматическое переключение** — переход на резервных провайдеров, когда основной нездоров
- **Панель состояния** — наглядные индикаторы в веб-интерфейсе

## Настройка

### Включение мониторинга

```json
{
  "health_check": {
    "enabled": true,
    "interval": "5m",
    "timeout": "10s",
    "endpoint": "/v1/messages",
    "method": "POST"
  }
}
```

**Параметры:**
- `interval` — как часто проверять состояние (по умолчанию: 5 минут)
- `timeout` — тайм-аут проверочного запроса (по умолчанию: 10 секунд)
- `endpoint` — проверяемая точка API (по умолчанию: `/v1/messages`)
- `method` — HTTP-метод проверки (по умолчанию: `POST`)

### Настройка балансировки

```json
{
  "load_balancing": {
    "strategy": "least-latency",
    "health_aware": true,
    "cache_ttl": "30s"
  }
}
```

## Стратегии балансировки

### 1. Переключение при отказе (по умолчанию)

Провайдеры используются по порядку, при сбое происходит переход к следующему.

```json
{
  "profiles": {
    "default": {
      "providers": ["anthropic-primary", "anthropic-backup", "openai"],
      "load_balancing": {
        "strategy": "failover"
      }
    }
  }
}
```

**Поведение:**
1. Попробовать `anthropic-primary`
2. При сбое попробовать `anthropic-backup`
3. При сбое попробовать `openai`
4. Если все недоступны, вернуть ошибку

**Лучше всего для:** боевых нагрузок с чёткой схемой «основной/резервный»

### 2. Круговой перебор

Равномерно распределяет запросы между всеми здоровыми провайдерами.

```json
{
  "load_balancing": {
    "strategy": "round-robin"
  }
}
```

**Поведение:**
- Запрос 1 → провайдер A
- Запрос 2 → провайдер B
- Запрос 3 → провайдер C
- Запрос 4 → провайдер A (цикл повторяется)

**Лучше всего для:** распределения нагрузки между несколькими аккаунтами, чтобы не упереться в лимиты

### 3. Минимальная задержка

Направляет запрос провайдеру с наименьшей средней задержкой.

```json
{
  "load_balancing": {
    "strategy": "least-latency"
  }
}
```

**Поведение:**
- Отслеживает среднее время ответа по провайдерам
- Направляет к самому быстрому
- Обновляет метрики каждые 30 секунд (настраивается через `cache_ttl`)

**Лучше всего для:** интерактивных и чувствительных ко времени задач

### 4. Минимальная стоимость

Направляет запрос самому дешёвому провайдеру для запрошенной модели.

```json
{
  "load_balancing": {
    "strategy": "least-cost"
  }
}
```

**Поведение:**
- Сравнивает тарифы провайдеров
- Выбирает самый дешёвый вариант
- Учитывает стоимость входных и выходных токенов

**Лучше всего для:** экономии и пакетной обработки

## Состояние здоровья

Провайдеры делятся на четыре состояния:

| Состояние | Доля успеха | Поведение |
|--------|--------------|----------|
| **Здоров** | ≥ 95 % | Обычный приоритет |
| **Ухудшен** | 70–95 % | Пониженный приоритет, но пригоден |
| **Нездоров** | < 70 % | Пропускается, если есть здоровые провайдеры |
| **Неизвестно** | Нет данных | Изначально считается здоровым |

### Маршрутизация с учётом здоровья

При `health_aware: true` (по умолчанию):
- Здоровые провайдеры получают приоритет
- Ухудшенные используются как запасной вариант
- Нездоровые пропускаются, если только не отказали все остальные

## Панель в веб-интерфейсе

Панель состояния доступна по адресу `http://localhost:19840/health`:

### Состояние провайдера

- **Индикатор состояния** — зелёный (здоров), жёлтый (ухудшен), красный (нездоров)
- **Доля успешных запросов** — процент успешных обращений
- **Средняя задержка** — среднее время ответа в миллисекундах
- **Последняя проверка** — время самой свежей проверки
- **Число ошибок** — количество недавних сбоев

### Хронология метрик

- **График задержки** — динамика времени ответа
- **График доли успеха** — динамика состояния
- **Объём запросов** — запросы по провайдерам

## Точки API

### Получить состояние провайдера

```bash
GET /api/v1/health/providers
```

Ответ:
```json
{
  "providers": [
    {
      "name": "anthropic-primary",
      "status": "healthy",
      "success_rate": 98.5,
      "avg_latency_ms": 1250,
      "last_check": "2026-03-05T10:30:00Z",
      "error_count": 2,
      "total_requests": 150
    },
    {
      "name": "openai-backup",
      "status": "degraded",
      "success_rate": 85.0,
      "avg_latency_ms": 2100,
      "last_check": "2026-03-05T10:29:00Z",
      "error_count": 15,
      "total_requests": 100
    }
  ]
}
```

### Получить метрики провайдера

```bash
GET /api/v1/health/providers/{name}/metrics?period=1h
```

Ответ:
```json
{
  "provider": "anthropic-primary",
  "period": "1h",
  "metrics": [
    {
      "timestamp": "2026-03-05T10:00:00Z",
      "latency_ms": 1200,
      "success_rate": 99.0,
      "requests": 25
    },
    {
      "timestamp": "2026-03-05T10:05:00Z",
      "latency_ms": 1300,
      "success_rate": 98.0,
      "requests": 28
    }
  ]
}
```

### Запустить проверку вручную

```bash
POST /api/v1/health/check
Content-Type: application/json

{
  "provider": "anthropic-primary"
}
```

## Уведомления через webhook

Получайте оповещения при изменении состояния провайдера:

```json
{
  "webhooks": [
    {
      "enabled": true,
      "url": "https://hooks.slack.com/services/YOUR/WEBHOOK/URL",
      "events": ["provider_down", "provider_up", "failover"]
    }
  ]
}
```

**Типы событий:**
- `provider_down` — провайдер стал нездоровым
- `provider_up` — провайдер восстановился
- `failover` — запрос переключён на резервного провайдера

## Маршрутизация по сценариям

Сочетайте мониторинг здоровья со сценарной маршрутизацией для разумного распределения запросов:

```json
{
  "profiles": {
    "default": {
      "providers": ["anthropic-primary", "anthropic-backup"],
      "scenarios": {
        "thinking": {
          "providers": ["anthropic-thinking"],
          "load_balancing": {
            "strategy": "least-latency"
          }
        },
        "image": {
          "providers": ["anthropic-vision", "openai-vision"],
          "load_balancing": {
            "strategy": "failover"
          }
        }
      }
    }
  }
}
```

Подробности — в разделе [Маршрутизация по сценариям](./routing.md).

## Рекомендации

1. **Выберите подходящий интервал** — 5 минут подходит почти всегда, 1 минута — для критичных систем
2. **Включайте маршрутизацию с учётом здоровья** — всегда в боевой среде
3. **Следите за ухудшенными провайдерами** — разбирайтесь, когда доля успеха падает ниже 95 %
4. **Комбинируйте стратегии** — переключение для «основной/резервный», круговой перебор для распределения
5. **Включите webhooks** — узнавайте о падении провайдера сразу
6. **Регулярно смотрите панель** — изучайте динамику, чтобы замечать закономерности

## Устранение неполадок

### Проверки не проходят

1. Проверьте, что ключи API провайдеров действительны
2. Проверьте сетевую доступность точек провайдера
3. Увеличьте тайм-аут, если провайдер медленный: `"timeout": "30s"`
4. Изучите журналы демона на предмет конкретных ошибок

### Неверные метрики задержки

1. Задержка включает сетевое время и время обработки на стороне API
2. Проверьте, не добавляет ли накладные расходы прокси или VPN
3. По умолчанию метрики кешируются 30 секунд (настраивается через `cache_ttl`)

### Переключение не срабатывает

1. Проверьте `health_aware: true` в настройках балансировки
2. Убедитесь, что в профиле заданы резервные провайдеры
3. Убедитесь, что проверки включены и выполняются
4. Посмотрите события переключения в веб-интерфейсе или журналах

### Провайдер завис в состоянии «нездоров»

1. Запустите проверку вручную через API
2. Проверьте, действительно ли провайдер недоступен (например, через curl)
3. Перезапустите демон, чтобы сбросить состояние: `zen daemon restart`
4. Изучите журналы ошибок и найдите первопричину

## Влияние на производительность

- **Проверки здоровья** — минимальные накладные расходы, выполняются в фоновой горутине
- **Кеширование метрик** — TTL в 30 секунд снижает число запросов к базе
- **Атомарные операции** — потокобезопасные счётчики для параллельных запросов
- **Без блокировок** — проверки не задерживают обработку запросов

```json
{
  "health_check": {
    "enabled": true,
    "custom_payload": {
      "model": "claude-3-haiku-20240307",
      "max_tokens": 10,
      "messages": [
        {
          "role": "user",

      ]
    }
  }
}
```

```json
{
  "providers": {
    "anthropic-primary": {
      "health_check": {
        "interval": "1m",
        "timeout": "5s"
      }
    },
    "openai-backup": {
      "health_check": {
        "interval": "5m",
        "timeout": "10s"
      }
    }
  }
}
```
